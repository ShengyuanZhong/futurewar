## 原日志根因

`temp/boss_attack_log.log` 是修正前的真实对局证据，SHA256 保存于下述回归报告。

- R78 前排 31035 在 `(6,21)` 可攻击基地最近格 `(9,21)`；后排 31036 在 `(5,21)` 距离 4，超过射程 3，并非当时能直攻却无故移动。
- 后排绕至 `(6,20)` 后，R79 再移动一步到 `(7,21)` 即可直攻基地，但旧 `base_weapon_obstruction()` 提前选中墙 `(7,20)`。R79～85、R94～111 合计 25 次拆墙，直到 R112 墙消失；前排同时未主动腾入口或占共同操炮位。
- R125 新的 45°射线 `(7,20)→(9,22)` 未命中失败缓存，但其它射线累计两次失败导致旧 `needs_close()` 全局强制贴基地。此时普通侦察单位已经死亡，不能从日志推断新站位确实空闲或为失败编造原因。

后排的临时通路投影仅用于判断是否值得原地短等，不用于下发移动或攻击；等待连续最多三轮，下一观测必须重新读取真实占用。正常移动或攻击重置等待计数。原实际移动失败格、攻击失败反馈与 `(目标ID,目标格,射击格)` 缓存仍保留，新未失败射线不受其它射线失败数量限制。

## 验证边界与复现

HTTP 输入只从日志提炼机器人、基地、炮台、入口及普通观察者的坐标；完整外墙环补齐、基地 HP1500、R82 再进入角色 HP80、伤害和成功反馈均为本地隔离假设，不是原官方完整报文或真实伤害重放。静态建筑/基地按已有规则可见，角色及炮台按普通单位视野筛选；BOSS 自身不提供视野。

在项目根目录运行：

```powershell
python CoreGeek/tools/validate_first_day.py --output reports/validation-v1.2.14.json
python CoreGeek/tools/smoke_boss_formation_flow.py --output reports/http-boss-formation-flow-v1.2.14.json
```

最终源码与官方规则 SHA256 均已核对。验证的是源码，未重新构建历史 wheel。占共同操炮位减少对方返回单人操三炮位置的机会，不能等同于保证对方无法在其它邻格操炮；新版效果仍需用户在官方平台复测。
