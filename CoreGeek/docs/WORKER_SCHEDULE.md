# 工人昼夜统一调度

版本0.3.8，2026-09-22。变更类别：策略优化，涉及R02移动、R03夜间禁建、R05避敌和R06交易/升级。用户已确认0.3.7为新基准，修改前保存了[完整源码快照](../../reports/baselines/v0.3.7-source.zip)与[逐文件SHA256清单](../../reports/baselines/v0.3.7-manifest.json)。官方原文、布局、升级顺序和基地不升级的要求不变。

## 1. 原因与变化

原`run_worker`在夜晚直接进入单独的`night_worker`采矿逻辑，没有调用白天的升级/采购流程。即使调用`consume`，旧逻辑也不允许夜间为升级券走到建筑旁；`buy_upgrade`还会用剩余白天时间阻止采购行程。因此黄昏到来可能把已携券返程的工人重新派往矿点，次日又折返。

现在普通工人昼夜进入同一个`worker(role)`经济流程。原独立任务与目的格记忆跨昼夜保留，不因`is_day`翻转清空；购物、卖矿、携券配送和采矿都继续按相同优先级决策。日照时间不再限制普通工人的升级采购，夜间路线仍必须满足避敌条件。每轮继续读取真实位置、背包、建筑等级和交易价格；不是盲目重放上一轮命令。

例如第200轮携带WeaponUpgradeVoucher1正在返回火箭旁，第201轮入夜后会继续配送并使用；收到实际等级变为2的观测后才使用WeaponUpgradeVoucher2。失败后仍针对实际一级建筑重试一级券。第260→261轮跨黎明同样不会把普通配送任务直接改为采矿。

## 2. 优先级与夜间限制

`Strategy.run()`保留开拓者先控炮、每人每轮一动作、低血量优先使用已持有药剂的流程。每名工人进入`run_worker`后：

1. 处理协作让行及短暂等待，紧急相邻维修仍可打断让行等待。
2. 若已经全部升级完成，执行双维修岗位；否则第三天起的指定维修工在夜间执行守墙岗位。
3. 普通工人先避开未被墙掩护的威胁，清理占用的建筑位/P站位。
4. 白天才执行开局建造链和维修工的备货/黄昏返岗约束。
5. 进入昼夜共用的经济流程。

经济流程顺序：白天补墙/筹石 → 商店旁补齐当前阶段的券 → 使用或配送已有物品 → 白天补炮 → 卖矿 → 采购升级券 → 采矿。缺墙时按每人的石头配额筹备，卖矿保留石头；夜间无可执行经济动作时尝试沿安全路线进入墙内，否则等待。

| 行为 | 白天 | 夜间 |
|---|---|---|
| 采矿、卖矿、批量买券、使用/配送升级券 | 正常经济优先级 | 相同优先级，普通行程要求安全路线 |
| 建造火箭、建造/补建城墙 | 仅工人，遵循原开局/补缺顺序 | 禁止；不会为了建造而前往建造位 |
| 第一台火箭集中升级、分组升级城墙 | 按原阶段 | 同样按原阶段，不越级、不升级基地 |
| 第一天的城墙升级 | 不安排 | 仍不安排；天数限制不是日照限制 |
| 普通工人黄昏返岗 | 不强制 | 不因入夜而放弃安全配送或购物 |
| 指定维修工、最终双维修 | 备货、维修、必要返岗 | 危墙优先，升级行程限定墙内通路；不新发起外出购物 |

官方任务书规定`build`仅工人白天可用，未把`buy/sell/use/collect`限定在白天。`build_weapon/build_wall/rebuild_wall`在策略入口检查日夜；`ActionPlan`继续保留独立规则校验。没有放宽动作合法性来实现“昼夜相同”。

## 3. 维修工如何兼顾升级

`WallGuard.on_duty(role)`顺序为：处理严格低于30%的危墙 → 若尚在墙外安全商店旁，买足当前缺少的修复包 → 尝试墙内升级 → 回到/保持维修岗位。

`on_site_upgrade(role)`要求角色已经位于墙内8格通路，且当前位置未受未遮挡敌人的威胁。它调用`consume(..., allowed=inner_cells())`；可沿内侧走到当前升级阶段的墙旁，或从内侧可操作的站位升级火箭。目标若必须走出墙内才能操作，就留给普通工人或白天处理；不会为升级任务丢掉维修职责。危墙维修优先于常规升级配送。

例外补货只针对已到安全商店旁的工人：避免黄昏刚到商店就空手返回。已有库存达到目标、钱不足、包满、商品不存在或商店位置暴露时不购买；之后仍返回岗位，不继续沿途采购升级券。白天安排新补货行程仍检查往返时间，夜间不从墙内发起新购物行程。动态备货、预算预留和双维修时的采购分工沿用0.3.7。

这意味着“统一策略”保留了角色职责约束：普通工人可以夜间配送，维修工只能在守墙范围内兼顾升级。机器人逼近、墙被毁、矿点消失、背包满、岗位分配变化和更紧急维修都可以改变原任务；不承诺任何地图绝不折返。

## 4. 修改位置与函数

| 位置 | 函数/参数 | 作用 |
|---|---|---|
| `src/agent/brain.py` | `run_worker(role: Unit) -> None` | 昼夜共用的单工人入口，先处理职责和安全约束 |
| 同上 | `worker(role) -> None` | 共用经济优先级，采集末尾按缺墙配额保留石材 |
| 同上 | `night_worker(role) -> None` | 兼容旧调用；只转到`run_worker`，没有独立夜间经济策略 |
| 同上 | `consume(role, allow_travel=True, allowed=None) -> bool` | `allow_travel=False`只原地用物品；`allowed`限制建筑升级行走范围，默认None不限范围；建筑物品仍必须相邻 |
| 同上 | `buy_upgrade(role) -> bool` | 保持阶段、批量、容量、库存与预算检查，去掉普通采购日照截止条件 |
| 同上 | `build_wall/build_weapon(role) -> bool` | 夜间直接False，不安排建造行程；白天逻辑保留 |
| `src/agent/wall_guard.py` | `on_duty(role) -> None` | 夜间值守入口，紧急维修/到店补货/内侧升级/待命 |
| 同上 | `on_site_upgrade(role) -> bool` | 仅墙内安全位置尝试当前阶段升级，可沿内侧走动 |
| 同上 | `daytime(role) -> bool` | 黄昏返岗前也允许内侧危墙维修和升级，不为原地能做的事空等 |
| `tests/test_worker_schedule.py` | 16个回归案例 | 昼夜连续性、交易、升级失败反馈、守墙及安全/建造限制 |

bool为True通常表示本轮已安排动作或合法协作等待，未必已经成功使用物品。成功与库存消耗始终以平台下一轮观测为准。

没有新增配置参数、请求字段、路由或外部依赖。`return_margin`仍用于开拓者回防、任务时间和维修工补货/返岗预算，不再限制普通工人的升级采购。`repair_*`与`sell_batch`含义不变。

## 5. 日志、验证与边界

服务日志`worker_jobs`中的`use:WeaponUpgradeVoucher1`、`buy_upgrade`、`sell`、`collect:stone`可以跨昼夜保持；`return_guard/guard_post/repair`表示岗位接管。若配送被中断，先看真实机器人、缺墙、背包与维修身份，再检查是否存在协作让行或无安全路径。

新测试覆盖两侧镜像用券、跨黄昏/黎明配送和销售、黄昏继续购物、夜间购券及批量墙券、按失败/成功观测逐级升级、矿点连续、危险采购与配送受限、夜间缺炮/缺墙禁建、内侧走动升级、危墙抢占、到店安全补货与暴露时不买。两项旧“夜里有钱仍只采矿”的预期随需求更新；官方动作校验不变。

测试结果见[0.3.8验证报告](../../reports/VALIDATION-v0.3.8.md)。本地案例和合成观测不等于官方完整对局，不能据此宣称实际胜率或路程减少百分比；城墙掩护依旧是用户实战反馈支持的策略假设。

0.3.9保留本版昼夜调度，另修复待建/缺墙格的路径与清理冲突，见[实战日志往返修复](WORKER_PATH_FIX.md)。
