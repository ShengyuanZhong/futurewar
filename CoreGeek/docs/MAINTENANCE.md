# 建筑升级、回血与城墙补建

版本：0.3.3，2026-09-21。用户指定0.3.2为当前表现最好的基准，本次只修改其上的维护策略。变更类别为策略优化，涉及R03建造材料、R06升级券与满血恢复；不修改任务书、接口或官方示例。

## 1. 基准版本

修改前的源码、文档和历史报告已保存为[0.3.2源码快照](../../reports/baselines/v0.3.2-source.zip)，[逐文件SHA256清单](../../reports/baselines/v0.3.2-manifest.json)记录原始内容。快照不包含缓存、构建目录、旧wheel和本地私有配置；[0.3.2 wheel](../dist/coregeek_futurewar-0.3.2-py3-none-any.whl)单独保留。

## 2. 升级阶段

仍先完成开局三火箭和初始围墙。第一天（1–130回合）只购买/使用武器升级券，先补齐所有一级武器的2级，再把2级武器升3级。即使已有墙券/基地券，或基地残血，也不在第一天提前使用这些券。

第二天（从131回合）起按观测中的未完成阶段推进：

| 顺序 | 条件及目标 | 购买/使用物品 |
|---|---|---|
| 1 | 存在1级火箭，先全部升2级 | `WeaponUpgradeVoucher1` |
| 2 | 城墙全部补齐，1级墙按迎敌方向由前到后升2级 | `WallUpgradeVoucher1` |
| 3 | 火箭全部升3级 | `WeaponUpgradeVoucher2` |
| 4 | 城墙按同样方向全部升3级 | `WallUpgradeVoucher2` |
| 5 | 武器和墙均已满级、无缺墙后，基地1→2→3 | `StationUpgradeVoucher1/2` |

第一天已升3级的火箭会自然跳过对应阶段。兼容旧混合炮型：武器阶段也包含已有加特林/电磁炮，用券时同级优先火箭。基地残血不再抢占武器/墙的升级预算。

阶段基于**实际观测**重新计算，不另存容易失效的“已经升完”标志。建造区启用而武器少于三座时，先补炮；缺墙会阻止进入墙升级及基地升级。新补建的一级墙自动回到墙1→2→3的阶段，不会因开局已完成而漏掉。

升级阶段金币不足时继续经营筹资，不用便宜的墙券或基地券跳过当前阶段。商店没有当前所需券时同样等待，不虚构商品。仍使用报文中的实时价格，并保留补炮金币；同回合卖矿所得不计入购买预算。

## 3. 城墙由前到后、升级兼顾回血

方向与U形布局一致，按基地实际左右位置决定：

- 左侧基地：墙的x坐标从大到小。
- 右侧基地：墙的x坐标从小到大。

原图基地为(6,7)时，每轮墙升级的列顺序为x=9的6面墙，再x=8、7、6各2面；3级升级重复这个顺序。只处理当前等级最靠前的未完成一列，等待下一轮观测确认该列全部升级后才进入下一列。

同列先处理剩余血量比例较低的墙，再考虑工人距离和建筑ID。已有有效升级券优先于`WallFixer`，避免先修满再升级。任务书规定升级成功后恢复满血；Agent只发`use`，不会自行改写等级或血量，成功/失败以之后的报文为准。

0.3.3原有修复包库存可用于残血墙，升级动作优先。0.3.4新增维修工主动备货与夜修：第三天起备5包、墙血严格低于30%时使用，维修工白天保留夜修库存；其他角色仍沿用本节用券逻辑。详见[工人避险与夜修](WORKER_SAFETY.md)。

## 4. 城墙被毁后的补建

`missing_walls()`用模板墙格减去存活己方墙的位置；墙血量为0或已从报文删除，都会形成缺口。`opening_complete=True`不再影响缺口检测和石头保护。

开局完成后，工人白天优先级为：

1. 持石时前往并补建缺墙；只在实际到达、目标未占用且背包确有石头时提交build。
2. 需要补墙但本人石头配额不足时，优先采石；背包满时只卖非石头矿物腾空间。
3. 没有可安排的补墙工作时，再用券、补炮、卖矿、购券和常规采矿。

仍沿用`stone_targets()`在工人间分配石头需求，避免另一工人已经备足时重复筹同一批材料。同轮`goals`及`ActionPlan`的目标预留防止两人重复造同一格。被占或无路可达的缺口不会强制输出非法建造动作；后续观测变化时继续尝试。

夜间不建墙，缺墙时保留背包中的石头，石头不足者继续采石，第二天再修建。原模板的维修通路和后方开口保持。补墙后只有下一轮看到存活墙才认为缺口补齐；新墙按官方规则从1级开始。

## 5. 函数、参数和状态

全部新增/调整入口位于`src/agent/brain.py`：

| 入口 | 参数 / 返回 | 用途 |
|---|---|---|
| `upgrade_candidates()` | 无参数，返回`list[Unit]` | 第一个未完成升级阶段的存活建筑，空列表表示当前不允许升级 |
| `upgrade_name(building)` | `Unit`→物品名字符串 | 按类型和当前等级匹配Weapon/Wall/Station券 |
| `wall_depth(building)` | `Unit`→int，小值更靠前 | 左侧取`-x`，右侧取`x` |
| `building_max_health(building)` | `Unit`→int | 基地`1500*level`，炮/墙`500+500*level`，仅用于残血比较 |
| `consume(role, allow_travel=True)` | 角色、是否允许配送移动→bool | 统一阶段用券，墙仅选当前前列，优先升级回血，再考虑已有修复包 |
| `buy_upgrade(role)` | 角色→bool | 按同一阶段采购，检查库存、实际价格、容量、补炮预算及返程时间 |
| `rebuild_wall(role)` | 工人→bool | 白天优先补缺口或筹石；True表示本轮已安排动作 |
| `worker(role)` | 工人→None | 在普通经济/用券之前调用补墙逻辑 |
| `night_worker(role)` | 工人→None | 只要缺墙就保护石头，开局完成后也生效 |
| `maintenance_claims` | 本轮`set[int]` | 记录已安排用券/配送的目标，减少两名工人同轮追同一建筑；不跨回合持久化 |

采购需求为当前阶段尚未在本轮提交升级的建筑数量；库存统计所有存活角色的背包，加上本轮buy数量，减去本轮use数量，足够时不再买。防止一个工人携券途中另一个继续超买，也防止同回合两次采购超过需求。预订配送目标不会假装扣券或升级成功；`ActionPlan.upgrade_targets`继续禁止同轮重复升级/修复同一建筑。

本版无新配置字段、无新HTTP路由；调用方法不变。重启服务即可加载源码变化。旧局继续传递真实递增回合与实际库存/建筑状态，程序会据此重算阶段。

## 6. 回归验证

`tests/test_maintenance.py`覆盖第一天限制、完整阶段、低血基地不插队、两侧前后顺序、升级优先回血、购券库存去重、同轮目标互斥、失败不推进、被毁/删除墙补建、夜间留石和重建后重新升级。多轮配送案例用实际服务生成动作，在单工人夹具中反馈购买、移动、升级，验证完整券序列以及每次墙升级的列顺序；该夹具不模拟完整比赛和战斗。

原先“第一天买基地券”的旧策略案例改为第二天、禁用默认建造区域的独立购买/用券协议场景；第一天不得买/用基地券由新增反例覆盖。原U形图样和开局测试继续执行。

结果与命令见[0.3.3验证报告](../../reports/VALIDATION-v0.3.3.md)。官方实战收益仍需后续实际测试。
