# 三火箭开局与夜间分工

当前版本为0.3.7：本文开局布局与冷却保持；升级与补建见[建筑维护](MAINTENANCE.md)，新增工人避险、批量采购与第三天夜修分工见[工人策略](WORKER_SAFETY.md)。

版本：0.3.2，2026-09-18。变更类别为策略优化，依据用户首轮测试反馈；受R01、R03、R04、R06、R07约束。官方原文没有修改。

## 1. 本版目标与启动前提

初始75金币优先建三座火箭发射台，每座25金币。两名工人随后采够配置城墙所需的石头，白天建墙；确认防线完成后恢复卖矿、买券、升级等策略。第一晚开始由开拓者负责三炮轮换，两名工人继续采矿。

默认`loadout`已改为：

```json
{"loadout": ["rocket", "rocket", "rocket"]}
```

配置是启动时读取的。若原本的外部配置仍写着混合炮型，它会覆盖新默认值，应同步修改并重启服务。已经存在的旧炮不会被自动拆除或覆盖。

**默认无需建造配置即可运行。**按用户“基地周围都可以建造”的明确要求，`allow_base_surroundings`默认true，`layouts`默认空字典。程序依据当前基地的位置生成候选区，再选择三炮和城墙位置；不再因为缺少官方坐标而跳过开局建设。

`app/config.py:base_surrounding_offsets(kind, mirrored=False)`按用户设计图生成固定偏移。默认采用用户设计图的12格U形墙与后排竖排三火箭，墙与基地之间保留一格宽维修通路，后方开口；开拓者站在中间火箭后侧P。按实际基地所在左右半区决定是否水平镜像。完整相对坐标、两侧示意图、关键函数及边界见[U形布局说明](U_LAYOUT.md)。绝对位置过滤地图边界、基地、矿点和其他非空地中立点，角色占用由每轮建造检查处理。

这是用户授权的本地布局假设，没有伪装成官方核验坐标。若提供`verified:true`的自定义布局，优先使用它；旧模板的verified:false空布局则使用默认区域。只有显式关闭`allow_base_surroundings`且没有有效自定义布局，或当前没有基地/可用格时，才会进入`unconfigured`。自定义布局应至少保留三处有效炮位。

## 2. 开局阶段

`Strategy.opening_stage()`只读取当前观测，未把发出的建造命令当作已经成功。

| 阶段 | 进入条件 | 工人白天行为 | 转移条件 |
|---|---|---|---|
| `unconfigured` | 显式关闭默认区域又没有自定义区域，或无基地/可用格 | 常规策略 | 恢复默认配置或提供有效布局 |
| `towers` | 开局未完成且存活武器不足3座 | 优先靠近和建炮；不买券、不先造墙 | 后续观测确认3座存活武器 |
| `stockpile` | 三炮已有，墙未齐，工人尚未满足石头配额 | 缺额者采石，已满足者向待建墙靠近 | 工人满足本批配额 |
| `walls` | 三炮已有，本批石头已齐 | 携石工人建墙或靠近墙位 | 全部配置墙出现在观测中；缺材时回到stockpile |
| `complete` | 已观测三炮及全部配置墙 | 常规经济、升级、补炮、补墙 | 本局保持完成；新局重置 |

两个工人每人每轮最多执行一个动作，初始即使就位也最多同时造两炮；第三炮在后续轮次补齐。需要行走、位置被占或动作失败都会增加轮数。规划尽量缩短建造距离，但没有真实地图和结算回放，不能承诺固定第几轮完成。

若初始/中途观测金币已不足25，允许先采矿、卖矿筹资；同轮预期销售收入不计入造炮预算。低血量且已有Medicine时允许优先用药。

完成后的建筑损失由白天常规`worker`流程补建，不重新封锁全部经济。中途重启会丢失内存完成标记，再按当前观测评估阶段。

## 3. 石头分配与保护

`missing_walls()`计算已配置但尚未存在存活己方墙的格子；每格需要一个石头。`stone_targets()`返回`{工人ID: 所需石头数}`：

1. 优先把工人已经持有的石头计入缺墙预算。
2. 对剩余需求，在不超过各自剩余容量的前提下均摊。
3. 需求超过两人合计容量时，分批攒石和施工。

例如还缺4面墙、两个工人均无石头且容量充足，各需2块石头。两人都达到配额后才开始施工；工人先完成份额时可以向墙位移动。若一人已带4块，不再让另一人重复采4块。

开局施工所需石头不按普通`sell_batch=12`阈值出售。`sell(role, keep_stone=True)`过滤石头，只卖其他当前可售矿物，给满背包工人腾空间。程序不自动丢弃商店物品；若背包被不可售物品占满，需要在后续策略中另行处理。

天黑后停止建造，但继续采石；石头足够时可以采其他有价值矿物，并把墙材留到下一个白天。

## 4. 炮位和操控格

`construction.select_defense_layout(turn, settings, previous)`规划`DefenseLayout`：

| 字段 | 内容 |
|---|---|
| `tower_sites` | 在Settings提供的自定义/默认建造格内选择已有炮加待建炮的位置，总计最多3处 |
| `operator_pos` | 优先与三炮都相邻的空地Pos，找不到时可能为None |
| `shared_control` | 该规划操控格是否覆盖所有选定炮位 |

默认图样可用时固定后排三炮和图中P，以免每次换炮都移动。自定义布局或既有炮不兼容图样时，沿用合法候选格内的共同站位规划。共同站位排除建筑、预定墙格；选定后保存在`GameMemory.defense_layout`。暂时站在炮位上的角色会尝试移开；静态障碍改变或可用炮位数量恢复时会重选不完整布局。

`Strategy.route`禁止角色进入规划炮位，工人额外避开操控格。`clear_build_cell`让已占建筑格/操控格的角色移开。建墙前`wall_keeps_exit`检查已可达的商业/任务路线及开拓者到操控格的路径，避免明显封路。

`shared_control=True`只代表规划具备共同邻格；当前是否被占、能否到达，由`control_position`及BFS每轮检查。如果合法区或已有炮不允许三炮共用站位，开拓者仍可逐炮移动操作，日志会显示相应布局标记。移动和攻击不能同轮执行，因此输出频率可能下降。

## 5. 夜间三炮轮换

`pioneer_should_defend`的条件为已有存活炮，并满足以下任一条件：已经入夜，或者剩余白天轮数不大于到操控格的实际路径成本加`return_margin`（默认4）。工人不参与黄昏回防。

`operate_weapons`逐轮检查：

1. 炮仍存活，与开拓者切比雪夫距离不超过1。
2. 观测中的`cooldown == 0`。
3. `choose_targets`能找到符合射程和等级数量的攻击目标。
4. 在合格炮中选择预计有效伤害最大者，同分按武器ID稳定选择。

响应以**武器ID为key、开拓者ID为controllerId**；开拓者本轮不会另发移动动作。两名工人可以分别采集或移动。

冷却遵守任务书的“发射后3轮空窗”，程序不自行计时缩短。以下是三炮都可在同一格操控、始终有合法目标、各次估值相当时的示例：

| 观测回合 | A冷却 | B冷却 | C冷却 | 开拓者动作 |
|---|---:|---:|---:|---|
| 71 | 0 | 0 | 0 | 发射A |
| 72 | 3 | 0 | 0 | 发射B |
| 73 | 2 | 3 | 0 | 发射C |
| 74 | 1 | 2 | 3 | 原地等待 |
| 75 | 0 | 1 | 2 | 发射A |

这是基于给定冷却报文的测试序列；真实平台返回什么冷却就读取什么。三炮并不允许单人同轮连发三次。冷却期间不写虚构`idle`指令，也不会把工人调回操炮；开拓者死亡时当前策略仍保留工人采矿分工。

## 6. 任务、宝藏与防守优先级

TurnService先构造Strategy并计算`defense_due`，再调用`TaskService.active`。尚不需回防时，活跃任务继续保持开拓者站位；需要回防时停止任务prompt、答案和executeCmd输出，把开拓者交给防御逻辑。

离开任务点可能使任务结束，官方`phaseTask`及结算是最终依据，程序不伪造“暂停任务”。新任务的时间预算包含预计返程；突发阻挡等仍可能要求放弃任务回防。

开局阶段不为宝藏花掉造炮金币。开局完成后，宝藏也必须让位于已有炮的黄昏/夜间防守；没有防守责任时才能按既有时间窗口策略行动。

## 8. 本地调用新策略

在项目根目录直接启动，新默认布局不需要任何额外配置：

```powershell
python CoreGeek/main3.py 8080
```

只有需要自定义时才添加`--config CoreGeek/config.local.json`。Postman使用：

- 健康检查：`GET http://127.0.0.1:8080/health`，无Body。
- 回合决策：`POST http://127.0.0.1:8080/`，`Content-Type: application/json`，Body选择raw/JSON，粘贴完整的一回合官方报文。
- 响应读取`roleCommandMap/prompt/executeCmd`；无需额外添加router、阶段或布局字段。

服务兼容任意POST路径；推荐固定使用`/`。同队伍同回合相同内容会返回缓存，不会重新推进策略；修改相同轮号的报文会收到400。对比不同输入时重启进程，连续回放则按真实轮号递增并提供实际结算后的下一轮观测。只连续调用HTTP不会自动移动、建造或递减火箭冷却。
