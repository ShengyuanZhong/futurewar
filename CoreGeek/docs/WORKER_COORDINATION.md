# 工人独立任务、协作让路、城墙掩护和动态备货

本文件记录0.3.7工人协作机制；0.3.8的[昼夜统一调度](WORKER_SCHEDULE.md)沿用这些机制。2026-09-22。基于用户实战反馈调整工人控制，涉及R02移动、R03角色与城墙、R05机器人威胁、R06补给。升级顺序、基地不升级、三火箭/U墙布局与任务模块保持。修改前源码保存于[0.3.6快照](../../reports/baselines/v0.3.6-source.zip)。

0.3.9统一了待建/待补墙位在寻路和清理中的预留，并增加实际位置往返诊断；原因与日志证据见[路径修复](WORKER_PATH_FIX.md)。

## 1. 两个工人分别控制

新增`src/agent/worker_coordinator.py`，由`Strategy.run_worker(role)`分别控制实际工人ID。角色仍每轮各输出一条官方动作；这是同一服务内的确定性分工，没有增加LLM调用或多线程控制。

`GameMemory.worker_tasks[worker_id]`保存每个人的独立任务，字段如下：

| 字段 | 含义 |
|---|---|
| `kind` | 当前用途，例如collect:stone、build:wall、buy_upgrade、repair、guard_post、repair_supply、yield |
| `target` | 矿点、建筑、商店格集合或让路对象；不是把两人绑定到同一个全局目标 |
| `goal` | 当前任务的交互站位/目的格 |
| `round` / `position` | 最近规划轮次及当时实际位置 |
| `moving` / `stalled` | 是否等待移动完成；连续未移动计数，最大8 |
| `recent_positions` / `oscillating` | 0.3.9新增：最多4个连续实际位置及两格交替标记；仅诊断，不随机改道 |
| `yield_until` | 让路后的短暂等待截止轮，默认让路后两轮 |

任务记忆随每队会话保留。目标仍合法、安全且可达时继续去原来的目的格；目标失效、矿点刷新、风险改变或停滞时重新规划。死亡角色与超过两轮未更新的记录释放，不占住复活后的任务或其他人的目标。

矿点选择先考虑是否已由另一工人负责，再考虑自己的已有任务、价格与路线。存在多个可用矿点时尽量分开；只有一个矿点时仍可分别站在不同相邻格采集。目的格使用独立预留，避免两人持续抢同一个交互位置。无安全矿点或满背包时仍沿用原策略切换任务。

## 2. 卡位处理与同时移动规则

普通寻路仍把当前活单位视为障碍，保持八方向移动和切比雪夫距离。遇到己方工人堵路时，额外计算一条“临时忽略己方工人”的诊断路线，只用于确定堵路者，不据此直接输出穿人动作。

若下一步被同伴占据，协调器寻找堵路工人周围合法的侧移空格：避开当前占用、已预留目的格、炮位、待建/待补墙位、P站位和对方目标；不增加堵路者当前危险值。维修工若已在墙内，只能在墙内侧移。侧移后还会检查让出的路线是否仍能到目标。

本轮先让堵路者移动，等待者保留本轮；下一轮读取真实位置后才通过原堵路格。让路者短暂停留，减少立刻回头再次堵住同伴的情况。已经领到其他动作的角色不被取消，能立即修危墙的人优先维修；让路等待期间若出现可立即维修的危墙也会解除等待。

没有侧移空位、静态障碍封路或当前路径仍不可用时等待/重规划，不发互换、同目标或穿占用格的动作。连续停滞者在下一轮工人规划顺序中提前，避免总被固定ID顺序挤到后面。既有`ActionPlan`的官方动作校验没有放宽。

这解决的是有可用避让空间的常见工人卡位，并不承诺任意封闭地形都有解；当前不采用同时跟入本轮刚腾出的格子的乐观假设。

## 3. 城墙掩护判断

此前`robot_danger`对机器人周围3格及额外1格警戒区统一加风险，忽略了城墙，可能让维修工远离岗位。本版按用户实战反馈，把仍存活且实际挡在机器人与候选位置之间的己方墙计作掩护。

`wall_shelters(start, end, walls)`检查两格中心连线是否穿过墙格内部；仅擦到墙角不算掩护。对每个机器人分别判断：被墙挡住的机器人不向该格叠加风险，其他未被挡住的机器人仍贡献风险。墙HP=0、被删除、缺口方向、机器人已经绕入同侧时，不会仅因“这个位置在基地附近”就宣告安全。即使墙残血，只要当前仍存活，仍是掩护对象，同时可以触发维修。

这是根据用户提供的对局行为加入的寻路策略，不是新增官方伤害公式，也没有改写任务书。它不修改机器人真实攻击、墙承伤或未来移动；城墙倒塌后的下一份观测会立即重新评估。公开任务书未完整定义机器人弹道/选敌细节，策略收益仍需实际平台回放确认。

## 4. 分区值守与堵门时的处理

完成全部升级后，两名存活工人按ID稳定分工：较小ID负责基地上半区，另一个负责下半区。默认图的待命点为(8,7)和(8,6)，也就是正中两块墙的内侧；基地在右侧时自动镜像。墙按y相对基地左上角分到上下责任区。

各自先维修责任区的危墙。如果另一人死亡、不在内侧或没有修复包，可以支援其墙段。同轮已修或已经安排前往的墙不会重复派人。双方岗位站反时，通过协作侧移就位，避免硬交换。存在未遮挡机器人威胁时可选择内侧更安全的位置；进入内侧后的巡护仍限制在原8格通路。

找不到内侧路线时，维修工尝试协作让路或等待，不再调用“寻找全图安全点”的逃离逻辑。普通外出采矿工仍保留避险撤离。此区别保留了维修任务，也意味着完全无路且暴露的维修工未必能保住生命，不能把等待当作绝对安全。

`GameMemory.dual_repair_active`记录本局是否曾达成双维修条件。曾达成后，即使夜间毁墙，两名工人继续负责剩余防线；次日白天若目标建筑尚未恢复，回到补建/升级流程。重新达标后恢复全天双维修。新局重置，不把上一局的岗位带入下一局。

## 5. 随天数与实际消耗增加备货

新增配置`repair_stock_per_day`，默认3，可设0关闭按天增长。原`repair_stock=5`变成维修起始日的基础库存。每人每日需求为：

```text
按天目标 = repair_stock + max(0, day - repair_start_day) × repair_stock_per_day
昨日消耗目标 = 上一游戏日确认成功使用的WallFixer数 + 2（昨日没有消耗则为0）
每日需求 = min(角色背包总容量, max(按天目标, 昨日消耗目标))
```

默认第3/4/5/6/10天分别为5/8/11/14/26包。比如昨日确认用掉17包，今天至少准备19包，前提是资金、剩余背包空间和采购时间允许。增加的是目标库存，已有库存会扣除，不是每天额外再买整批。

`repair_usage_today/repair_usage_previous`按工人ID保存确认消耗。只有上一轮确实发出`use WallFixer`且本轮`lastRoundRoleActionResults`明确为true才计数；失败或反馈缺失不猜作成功。先计入上一轮反馈，再滚动换日，因此黎明收到的最后一夜维修结果会进入昨日统计。跨多日缺报时不把旧消耗冒充昨天。

全部升级尚未完成时，第三天起原单维修工按动态目标备货，升级采购为缺包预留预算。全部目标完成后，仍把全部可支出金币投入修复包：先弥补各人的每日需求，再尽量均衡余量，受本人背包余量限制。昨日用包多者可能先获得更多库存。白天仍轮流购物和回岗，夜间不新发起外出购物；0.3.8允许已经在安全商店旁的维修工买足缺包再回岗。若两人资金足够，会超过每日最低需求备更多包；没有强行把已持有的包丢弃以符合目标。

| 配置 | 默认 | 范围/作用 |
|---|---|---|
| `repair_start_day` | 3 | 升级完成前开始单维修工分工的日期 |
| `repair_stock` | 5 | 基础目标，1–100 |
| `repair_stock_per_day` | 3 | 每日增长，整数0–100；最终需求按角色容量封顶 |
| `repair_threshold_percent` | 30 | 仍严格低于阈值才用包 |
| `return_margin` | 4 | 采购与黄昏回岗时间余量 |

## 6. 模块与关键函数

| 文件/函数 | 参数与返回 | 用途 |
|---|---|---|
| `worker_coordinator.WorkerCoordinator(strategy)` | 当前Strategy | 管理每个工人的独立任务、目标和让路 |
| `assign(role, kind, target, goal, moving=False)` | 当前角色、用途、任务对象、目的格→None | 更新该工人的任务记忆 |
| `move_to(role, goals, kind='travel', target=None, allowed=None, allow_risk=False)` | 候选站位、可选内侧范围及风险许可→bool | 正常寻路，必要时诊断堵路并安排让行 |
| `yield_blocker(requester, blocker, goal)` | 请求者、堵路者、请求目的格→bool | 安全侧移；只安排合法空格 |
| `hold_for_yield(role)` | Unit→bool | 让路后短暂停留，可被紧急维修打断 |
| `diagnostic_route(role, allowed=None)` | Unit/可选范围→Routes | 忽略其他己方工人来判断堵路，不能用于绕过ActionPlan |
| `grid.Routes(..., ignore_workers=frozenset())` | 新增可选工人ID集合 | 仅诊断时使用，普通调用仍完整检查占用 |
| `worker_safety.wall_shelters(start,end,walls)` | Pos、Pos、存活墙坐标→bool | 穿过墙格内部才算掩护 |
| `robot_danger(turn)` | Turn→Pos到风险值 | 每个机器人独立计算掩护，输出路线代价图 |
| `Strategy.run_worker(role)` | Unit→None | 单个工人的完整决策入口 |
| `WallGuard.home(role)` / `owns_wall(role,wall)` | Unit→Pos或None / bool | 分管上下岗位及支援判定 |
| `WallGuard.daily_stock(worker)` | Unit→整数 | 天数/昨日确认消耗共同决定目标 |

0.3.9另加`worker_motion`，分别记录实际位置、目标、计划动作和反馈。原服务日志`worker_jobs`：工人ID对应任务名、目的格及停滞次数；原`full_time_repair`、`repair_supplier`继续记录维修和采购状态。无需新增请求字段或HTTP路由，重启服务加载新版即可。进程重启不会恢复旧任务记忆，但会据当轮建筑和单位状态重新分工。

## 7. 验证边界

新增`tests/test_worker_coordination.py`覆盖两侧城墙掩护、倒墙/内侧敌人/多敌人/擦角、独立矿点、窄路侧移、无空位等待、岗位交换收敛、堵门不远逃、夜间毁墙维持双维修、死亡/过期任务清理、按天增长、实际成功消耗换日及配置边界。

原完整升级和开局测试保留；旧“第四天补4包”案例按新需求改为已有1包、补7包。没有改动升级顺序和动作校验来使测试通过。全部结果见[0.3.7验证报告](../../reports/VALIDATION-v0.3.7.md)。本地反馈夹具不代表官方完整对局，尚未验证实战胜率或极端拥堵下的全局最优调度。
