# v1.2.17 首日分矿与个人任务交接

2026-10-13。本版在[首日建墙调度](WALL_SCHEDULE_V1216.md)上修正两项效率问题：石矿最多只能采10次，两名工人应联合选择矿点；每名工人实际完成自己的施工段后就进入采购或侦察，不等待另一人的施工，也不转去普通收入采矿。

这是团队策略调整。矿区总量、每轮采集、移动、建造与交易权限继续依据[复赛任务书](../../32_docs/任务书.md)和[复赛接口文档](../../32_docs/接口文档.md)。官方文件和用户原始日志不变，正式程序与测试不依赖 `temp/`。验证范围仅为第一天，结果和源码哈希见[本版验证报告](../../reports/VALIDATION-v1.2.17.md)，不代表已完成新版官方对局。

## 日志根因

`temp/build_bug.log` 中，两个工人最初分别前往不同石矿：R10工人20012选择 `(36,4)`，R11工人20010选择 `(32,2)`。但R14工人20012改去同伴附近的矿点，R20～R23两人共同采矿，R24又一起转向另一矿。

旧选择逻辑只为当前工人比较是否已相邻、是否是旧目标、距离等局部条件。它区分两人的采集站位，却没有联合分配矿点，也没有解析矿区的 `remain`。因此“能在不同格一起采”被当作有效协作；对于17块墙的真实总材料需求，同一个最多10次的石矿无法供足，两人先聚集再一起换矿会浪费行程。局部可采判断也可能破坏另一人已经开始的有效预约。

施工后的另一问题来自全队完成门槛。工人的个人分段已完成，但采购与侦察仍检查整圈是否完成，导致先完工者继续走采矿经济分支或等待。个人分工要提高效率，后续任务的交接条件也必须使用个人真实施工结果。

## 观测矿点剩余量

实现位置：[src/agent/protocol.py](../src/agent/protocol.py)。`Turn.load()`继续保留 `zones: dict[Pos,str]`，另外从矿区元素的 `remain` 解析 `mine_remaining: dict[Pos,int]`。石、铁、铜矿都可保存该观测值，但本版联合分矿只用于首日日间筹石。

接口文档规定 `remain` 为剩余采集次数；任务书规定每矿最多采10次。策略使用当前报文值，不能把一个低余量矿点当成完整10石，也不能在发出 `collect` 后自行扣减或提前增加背包。矿点消失、采集成功、库存增长均由下一轮观测确认。

旧报文或本地输入缺少 `remain` 时，策略暂以10作选择的上限回退。这是兼容旧输入的假设，不是已观测到还有10石。诊断中的该矿余量为 `null`，同时输出 `unknown_remaining_fallback: 10`，便于区分真实数值和回退。

## 两人联合分矿

实现位置：[src/agent/stone_planner.py](../src/agent/stone_planner.py)。`StonePlanner.targets()`仍根据真正缺墙、工人的实际背包、容量和施工段计算每人的目标石头数量，不重复累计团队材料需求。`assignments()`在此基础上统一比较所有仍缺石工人的可达石矿组合。

每名工人的候选矿必须满足当前条件：类型为石矿、观测余量大于0、没有失败退避或停矿新闻、存在合法采集站位且实际路线可达。站位和路线继续考虑单位占用、同伴目标、本轮预约、车辆、危险与三炮建成后的外侧施工范围。不能以穿过将封闭内圈的短路代替真实外侧行程。

组合的比较顺序如下：

1. 优先避免两个需要筹石的人共享同一矿点。如果两人的可达候选可以形成不同矿的配对，就选择不同矿，不固定按地图左右或工人ID硬编码矿坐标。
2. 在分矿条件相同的组合中，保留有效的旧预约，减少途中掉头。两个旧预约已经不同且仍可执行时，不因出现更近矿点而每轮交换。
3. 比较各矿真实余量能覆盖多少个人缺口，再比较合法站位的总行程。这里的个人缺口是目标石数减去实际持石数，不能重复算整个17墙需求。

已开始的有效采矿行程不会仅因他人采集导致 `remain` 降低而立即掉头；可以先采剩余量，再在矿消失后换矿。矿点消失、零余量、失败退避、真实不可达、连续停滞或个人配额完成会使旧预约失效。下一次规划使用当前观测，不能将过期预约作为永久占矿。

只有一个可达石矿时，允许两人在不同合法站位采同一矿。这个回退保证有工作可做，不为了强制分矿让另一人原地等待；一旦可以形成不同矿的可行配对，再采用分矿。分矿不会把个人目标抬高为10，也不会采超过实际墙材需求的额外石头。

## 个人完成即进入下一任务

实现位置：[src/agent/wall_schedule.py](../src/agent/wall_schedule.py)、[boss_raid.py](../src/agent/boss_raid.py)与[raid_scouts.py](../src/agent/raid_scouts.py)。稳定的17墙分段仍沿用v1.2.16，完成判断改为真实三炮和该工人自己的未完成墙，不再要求同伴施工结束。

| 工人使命 | 个人施工结束后的行为 | 仍需满足的后续条件 |
|---|---|---|
| 固定采购工 | 立即赴实际商店，三任务未结束时在店附近准备 | 开拓者按2→1→2尝试三次任务后，按确认成功数冻结0～3张BOSS券，受实际金币、价格和容量约束；用券仍需真实侦察与当前共享视野 |
| 固定侦察工 | 立即前往敌基地探测阵型并持续提供视野 | 按真实可见炮台或已扫描武器格确认阵型；召唤机器人不能替代普通单位提供视野 |

只提交最后一堵墙的 `build` 不算完成；下一轮必须实际看到建筑。对手当前站在个人墙位上时可暂跳该墙，但不会把它记成已经建成。对手离开后仍可补建，首夜工人肉身补位和捣乱鬼接力保留。

`WallSchedule.release(role,mission)`保存已经转入下一任务的身份和回合。释放后不因另一人还在建墙又重新借用其施工段、转回普通采矿；另一工人死亡、离开使命或留下真实未建墙时，未释放的施工工人仍可按原接手规则处理。

如果侦察工成为唯一存活工人，首日日间暂时停止侦察，设置 `paused_for_construction`，并通过 `WallSchedule.reclaim(role)`恢复其施工身份，接手实际未建墙与筹石。不能仅保留“之前已派出”的记忆而让基地没有任何施工者。同伴恢复且个人应做施工完成后，再恢复侦察。

采购工未做完个人施工，但实际赴店购用截止已到时，继续优先购物，不追加返家预算。首日日间两工仍不提前回防；其它天经济、升级、动态修包备货与夜间维修保持原流程。本版没有改动三任务解题模块或BOSS攻击优先级。

## 关键函数与参数

| 位置与函数 | 参数、返回值 | 作用 |
|---|---|---|
| `protocol.py: Turn.load(payload)` | 官方请求字典 → `Turn` | 将矿区 `remain` 保存到 `mine_remaining`；原 `zones` 类型映射继续可用 |
| `StonePlanner.targets()` | 无 → `dict[int,int]` | 每名工人应实际持有的石头总数，结合个人施工段、真实缺墙、背包和容量 |
| `StonePlanner.options(role,return_cells=None)` | 工人、可选返岗格集合 → 候选列表 | 筛选当前合法可达石矿及实际采集站位；首日白天不扣返程预算 |
| `StonePlanner.assignments()` | 无 → `dict[int,Pos]` | 联合分配仍需筹石的工人矿点，优先不同矿、保留有效旧预约、比较余量与路程 |
| `StonePlanner.mine(role,return_cells=None)` | 工人、可选返岗格集合 → `bool` | 首日按联合分配选择矿；已邻近就采集，否则沿真实路线移动；未提交有效动作返回False |
| `StonePlanner.diagnostic()` | 无 → `dict` | 输出矿点预约、个人缺口、共享回退、观测余量和未知余量回退值 |
| `WallSchedule.assigned_missing(role,ignore_enemy_occupied=False)` | 工人、是否暂跳当前敌占格 → `set[Pos]` | 个人真正未建墙及应接手的无人施工墙；不以本轮建造指令代替观测 |
| `WallSchedule.construction_ready(role)` | 工人 → `bool` | 真实三炮已完成，个人可建墙已完成；当前敌占墙位暂跳 |
| `WallSchedule.release(role,mission)` | 工人、使命字符串 → 无 | 记录下一任务，避免个人完工后回头借墙或继续普通采矿 |
| `WallSchedule.reclaim(role)` | 工人 → 无 | 删除个人施工释放记录，使唯一存活且暂停侦察的工人接手剩余施工 |
| `BossRaid.worker_dispatch_ready(role)` | 工人 → `bool` | 首日启用分段时使用个人施工门槛；非分段场景保留旧完成判断 |
| `RaidScouts.refresh_dispatch()` | 无 | 分段状态准备后重新确认侦察工个人完成，分配/保持侦察使命和真实视野就绪状态 |

`return_cells`是已有通行与回防接口，未因本版分矿新增配置项。石矿数量、矿坐标、商店和敌基地位置均从当前输入读取；未知余量回退10与稳定预约停滞门槛属于策略兼容参数。

## 状态与诊断位置

跨回合状态位于 [app/service/memory.py](../app/service/memory.py) 的 `GameMemory`，由同一比赛会话保存；不写入官方报文，也不读取用户日志控制比赛。

| 状态位置 | 字段 | 含义 |
|---|---|---|
| `Turn.mine_remaining` | `Pos → int` | 仅本轮明确提供的矿区余量；缺失不伪造观测 |
| `GameMemory.stone_mining` | `round`、`assignments`、`shortage`、`shared_fallback` | 最近联合分矿回合、工人对应矿点、实际个人缺石量、是否必须共享矿点 |
| `GameMemory.worker_tasks` | `kind/target/goal/moving/stalled/stone_quota` | 真实采集或施工任务、矿/墙坐标、合法交互格、行程与个人目标石数 |
| `GameMemory.sealed_home['wall_schedule']` | `arcs/frontier/released` | 稳定施工段、下一墙及已经进入采购/侦察的个人释放记录 |
| `GameMemory.raid_scouts` | `worker_id/worker_status/personal_dispatch_round/paused_for_construction` | 固定侦察工、等待/派出原因、个人派出回合及唯一存活工人暂停侦察标记 |
| `GameMemory.boss_raid` | `personal_construction_approved_round/departure_reason` | 采购工个人完成确认与 `personal_walls_ready` / `shop_deadline` 出发原因 |

排查时将 `stone_mining` 与 `wall_schedule`、`worker_jobs/worker_motion`、`raid_scout`、采购 `decision` 放在同一回合核对。`target`是计划矿/墙，`goal`是交互站位，两者都不能代替角色实际坐标；日志中的预约、候选和指令不代表动作已经成功。

## 验证与后续修改

本版验证重点是两个10石矿与17墙需求、只有单矿时持续工作、低余量与旧预约、矿消失/失败/不可达后的释放，以及一人完工而另一人仍施工时的独立采购/侦察。连续HTTP场景、输入假设和实际结果见[首日验证报告](../../reports/VALIDATION-v1.2.17.md)。

后续调整分矿排序从 `StonePlanner.assignments()`开始；修改候选可达性从 `options()`开始；修改个人筹石数从 `targets()`开始；修改施工到下一使命的交接从 `WallSchedule.construction_ready/release`与 `RaidScouts.refresh_dispatch()`开始。保持下一轮实际反馈确认、购券截止和工人外侧路径安全，避免把局部距离优化再次变成两人追同一个矿或全队完成后才派出的串行流程。
