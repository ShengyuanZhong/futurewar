## 规则与策略的来源

- 同文§4.7.2/§4.7.3：BOSS为800HP、攻击力40、射程3；第一夜首回合生成，行为由召唤方指令驱动，黎明剩余机器人清除。
- [v2.0接口](../../32_docs/接口文档.md)§2.2/§2.3：`buy.num`可以批量购买；`use`每次只指定一个位置；每角色每回合至多一条指令，机器人以自己的ID执行`move`或`attack`。
- 用户转述工作人员确认：召唤机器人没有视野，也不能在同一回合移动并攻击。仍需常规单位提供共享视野。

机器人攻击受城墙阻挡沿用用户实战补充。炮台与基地内部占格的射线排除是针对已有非法攻击日志的保守规划；官方现有文档未完整定义所有建筑弹道和擦角细节，不能把该规划假设当成判题器规则。

## 第一夜战斗决策

每只存活且未眩晕的本方BOSS独立读取本轮观测。检查可见且存活的`rocket/gatling/railgun`八邻格，将其中`worker/pioneer`作为可能操炮者；不要求对手采用我方U形围墙和后排三炮模板。武器旁存在角色仍是候选推断，接口没有敌方当前`controllerId`。

1. **立即可攻击的炮手始终优先。** 同时满足当前射程、真实目标、墙遮挡、保守建筑射线检查及失败站位缓存条件的候选，优先直接攻击。直接候选按当前HP所需命中数、HP排序，旧目标只稳定并列选择。目标回血、换岗或另一工人进入炮旁时，每帧重查，不预测击杀。
2. **先筛成本，再比较候选。** 为所有炮手计算可达射击站位`post`，比较到该站位的真实八方向路径步数。只保留费用不超过剩余追击预算的候选，再按既有优先级选择；不会先选最低HP但遥不可及的一个炮手，把近处可攻击候选一起丢掉。费用计算到射击站位，不是机器人到炮手坐标的直线距离。
3. **低成本破墙可以替代长绕路。** 当前没有预算内射击站位时，评估当前射线的第一道敌墙或炮手旁的敌墙。费用为`到破墙射击位的步数 + ceil(墙当前HP / BOSS攻击力)`。不超过剩余预算才为炮手破墙；即使另有昂贵绕行路径，也允许这个短破墙方案。40HP墙一发即可形成候选，800HP墙需要20发，不能以“墙距目标很近”忽略消耗。
4. **昂贵或无效追击切换基地。** 所有炮手均不可达、可达射击位超过预算、或连续追位/非法攻击已经消耗预算时，转攻全局可见的存活基地。附近炮手仍存活不再构成无限追击的硬条件。
5. **基地聚焦维持4回合。** 回退当轮设置`SIEGE_FOCUS_ROUNDS=4`。随后暂缓重新追逐需要移动或破墙的炮手，避免在基地和远处目标间反复切换；已有直接可攻击炮手仍会立即打断聚焦，保留清理操炮者的最高优先级。

配置`boss_controller_max_walk`默认4，类型为int，允许0–30。它既限制单次可接受的射击站位步数，也作为连续追击的总预算。`0`表示只即时攻击当前可直接命中的炮手，不为其额外移动或破墙；没有直接目标时尝试基地。示例：

```json
{
  "boss_controller_max_walk": 4
}
```

连续回合中，上一帧仍在为炮手移动、破墙或没有收到合法炮手攻击反馈，就递增`pursuit_rounds`；剩余预算为`max(0, boss_controller_max_walk - pursuit_rounds)`。切换炮手不会借换ID重置这一段无效追击。上一帧`controller`阶段的`attack`获得明确合法反馈时，本段预算重新开始。这里确认的是动作合法性，不能据此宣称该发造成伤害；无反馈不会被当成合法攻击。

回退原因分别记录为`controller_unreachable`、`controller_detour_too_long`、`controller_chase_budget`、`siege_focus`。`siege_until`使用回合号；聚焦区间包含触发回退的当轮，达到结束回合后可以重新评估短追击。若本轮没有可见操炮者，直接尝试基地，不把“不可见”写成“全部击杀”。

## 基地占格与射击位置

基地传入位置为2×2建筑的左上角`(bx,by)`，实际占四格：

```text
(bx, by)     (bx+1, by)
(bx, by-1)   (bx+1, by-1)
```

`attack_base()`把四格都交给原射击规划，优先选从当前站位可以直接攻击的外露格；无需绕到左上角才射击。每只机器人仍只发送一个`targetPos`，不会把四格一次全部传入攻击指令。其它格上存在基地，不等于允许射线穿过基地内部再打更远的一格。

`RobotRaider.clear_shot()`在原`clear_attack()`之上检查可见炮台和基地的其它占格内部。纯角点接触不算这一层建筑内部阻挡；已有城墙闭区间检查保持原处理。射击位搜索也使用相同保守排除，并继续过滤占用、不可达、已失败站位及本轮移动预约。

`ActionPlan`的原机器人攻击门禁没有扩大为“所有建筑必然挡弹”：它仍检查夜间、未眩晕、一个真实敌目标、射程和中间墙。本轮新增建筑排除位于策略规划层，用于选择更可靠的射线。不会额外推断NPC或角色挡弹，也不会从`temp/`读取对手隐藏单位。具体角点、其它建筑遮挡和非左上角基地落点是否命中仍需官方实战核对。

## 两张召唤券的购买与部署

购买入口仍由`BossRaid.pioneer()`接管开拓者，限定第一天白天且`phaseTask`为空。正在执行的任务继续由原任务模块处理，经济充裕也不会打断当前任务。满足以下任一双部署依据后尝试两只：

- 第一日两个不同任务点有明确提交及奖励依据，记录于`task_points_succeeded`。
- 按本轮`weaponShopList`的真实BOSS券单价，经济足以覆盖两张所需金额。先从可花金币中保留尚未建齐三座炮的25金币/座，再计算券预算。

已有持券、部署记录和锁定的目标数量也参与判断；已取得一张时只计算还需补足的数量。日内账本最多管理两张，不能因为背包变化或生成位置旁移反复购买。

已明确确认只部署一张、累计取得一张且背包没有剩余券时，若白天后续奖励或卖矿使预算足够，仍可有限补购第二张；必须重新通过到店、使用、返岗、日限及出生点检查。两张已经批购时直接用剩余券，不重复赴店；旧版本推断的部署状态、未知历史或库存异常不会开放追加购买。

计划同时核对金币、容量、合法不同出生点、单日剩余召唤次数、到店路径及回防时间。商店行程预算为：

```text
到商店邻格步数 + 1次购买 + 计划use次数 + 回操炮位步数 + return_margin
```

返程路径以角色暂时位于商店邻格后的占用计算，不能用直线距离替代。已有持券无需重新计购买和赴店，但仍计每张券的一次`use`与必要返程。计划两只不可行时尝试一只；一只也不可行就交回原策略。不能为凑两只推迟开拓者回防，也不能透支未完成的三炮建设预算。

典型流程如下，示例`502`必须替换为当局真实开拓者ID：

1. 商店旁一回合发送`buy`，`name="BossRobotSummonOrder"`、`num=2`。
2. 后续观测确认实际背包增加后，在一个白天回合对第一处后方合法位置发送`use`，只传一个`targetPos`。
3. 再一个白天回合对不同位置发送第二次`use`。本方待生成位置和已确认使用位置共同参与排重。
4. 完成后返回己方原操炮位。夜间开拓者继续操控我方炮台，两只BOSS以自己的ID各自行动。

“第一天部署两只”指同一夜生成两只，不是同一角色同回合执行两次`use`。不会给`use`新增`num=2`或两个目标位置来绕过接口限制。双成功只是启用双部署的依据，仍必须有足够金币、空位和时间；不能根据任务成功凭空购买。

出生候选继续沿用真实敌基地优先、2×2整体镜像后备及已有后方排序。双方建造区域、NPC和静态占用排除不放宽。动态角色、矿或机器人占据请求点时，官方允许旁移；实际生成ID和位置始终以`teamOur.summonRobotList`为准，不能把请求点作为机器人下一帧真实位置。

## 任务成功依据与状态账本

`TaskService.active()`先结算上一轮提交，再归档/清理任务上下文。只有连续回合、原任务处于活动状态且上一动作确为`submitAnswer`、该动作反馈明确合法、没有错误码1/2/5、存在奖励增量依据，且当前控制器的完成判定成立时，才向`GameMemory.task_points_succeeded`添加`(提交所属日, task_x, task_y)`。采购仍要求实际`phaseTask`为空，不用任务描述消失本身代替成功证据。

奖励依据使用提交前保存的金币/总分基线；金币上升时排除同时发生`sell/catch/summonTreasure`的收入混淆。单凭任务描述消失、曾接取过任务或`lastRoundRoleActionResults=true`不会记录成功。接口没有直接给出该任务通过率，因此这个集合表示“有明确合法提交及奖励证据”，不证明答案100%通过，也不保证每一种并发积分来源都可完全归因。

`task_points_attempted`仍表示当日已确认接取过的点。两个点都尝试结束后，即使任务未获奖励也可沿用单券流程；双券资格可以由经济条件独立满足。任务prompt、执行沙盒和成功/失败经验固化流程继续保持。

`GameMemory.boss_raid`由观测、持券和关联反馈维护，主要字段如下：

| 字段 | 作用 |
|---|---|
| `history_known` | 是否有可靠本进程日内历史；未知历史时限制新增购买 |
| `deployment_ledger_confirmed` | 区分实际维护的部署账本与旧状态推断；有限补购第二张需要明确账本 |
| `target_count/acquired_count/deployed_count/bought_count` | 本轮目标上限、已管理取得量、已确认使用量、实际购买确认量；本策略管理上限两张 |
| `pending_buy` | 买券回合、操作者ID、原持券量与请求`num`，用于与后续真实背包和反馈关联 |
| `pending_use` | 用券回合、操作者ID、原持券量与请求出生点；等待后续反馈或消费证据 |
| `spawns/spawn` | 已确认使用位置集合与最近请求点；不代表真实夜间出生坐标 |
| `purchase_locked/purchase_closed` | 已部署后的购买约束（明确只部署一张时允许有限后补）和未知/矛盾库存的停止新增购买标志 |
| `failed_positions/inventory_warning/status` | 失败位置排除、库存/反馈不一致原因与当前状态 |

买券成功主要由实际库存增量确认，合法反馈不代替背包证据；明确失败且库存未变时可以重试。`use`以关联的合法反馈或一张券消费证据确认。明确失败时释放本地日限尝试和待生成位置，避免重复扣次数；未确认或库存异常时保守停止追加购买，不把异常缺券当成“需要再买一对”。

常见`status`为`shopping/buy_pending/summoning/summon_pending/deployed/order_missing/unknown_prior_deployment`。`deployed`说明已确认用券，不说明机器人已经生成或仍存活。实际日限由`GameMemory.summon_attempts`和`pending_summon_positions`继续管理，整个比赛仍按官方每日10张上限校验。

账本保存在当前进程的队伍会话中，未新增磁盘持久化。中途重启且无法重建既往部署历史时不新买，避免超过本策略的两张上限；已有持券可以在时间、容量与出生条件满足时继续部署。未知历史不能仅靠当前背包有券就认定此前从未使用其它券，夜间仍可按真实本方机器人列表控制。

## 侦察、留守与双机器人调度

v1.2.3的侦察分工继续：捣乱鬼提前赴敌基地后方；一名固定工人只有真实三炮、永久墙与所需临时围挡建齐且能及时到达时外派；另一名工人优先防御恶意占墙，否则正常工作。侦察角色不替代开拓者使用券，不在本轮移动后提前伪造下一帧视野。

`Strategy.run()`在英雄调度后遍历所有实际本方机器人。两只BOSS各有自己的`robot_raids[id]`和动作反馈，分别评估炮手/基地；共同使用`ActionPlan.reserved`，不会预约相同下一步，也不能走入另一只机器人当前占格。每只仍只有一次移动或攻击，不能同轮叠加。预算不足、眩晕、死亡或第一夜结束时沿用原退出处理。

双BOSS不能保证分别清空不同炮位，也不会用预计两发伤害在本地宣布目标死亡。下一帧依真实HP决定继续攻击、换目标或回退；两只的实际伤害、碰撞和旁移仍由判题器结算。

原INFO日志继续输出；`enable_robot_diagnostics=true`控制`robot_observation/robot_diagnostic`，`boss_raid`仍展示完整购买状态，`raid_scout`展示侦察分工。

| 日志字段 | 查看内容 |

| `firing_sweep.counts.building_blocked` | 被建筑内部射线排除的站位数量；纯角点不计入这一层阻挡 |
| `fallback_reason/siege_until/base_cells` | 为什么攻基地、聚焦到哪帧、基地四格候选 |
| `robot_observation.requested_spawns/target_count/deployed_count/owned_ids` | 两张券的确认使用位置、目标/确认数量与真实生成ID，三者含义不同 |
| `boss_raid`状态 | 关联`pending_buy/pending_use`、取得/购买/使用计数及`inventory_warning`，解释为何只买一张或停止追加 |

排查时把同一回合的`boss_raid/raid_scout/robot_diagnostic`关联起来：先确认双券是否真的入包并使用，再核对两只实际ID、视野中的炮手、预算、遮挡和动作反馈。`True`只说明动作合法；目标HP没下降、失去视野或某机器人从列表消失都应分别记录，不能仅凭日志中的意图宣称击杀。

新测试覆盖直接/短路炮手禁止随意打基地、不可达/昂贵绕路回退、廉价破墙、建筑内部与角点、2×2占格、批量购买与分帧使用、预算与库存反馈及多机器人预留。独立审计用手算正反例约束新策略，不通过调用生产选敌函数自行证明结果正确。累计追击和聚焦行为由连续回合测试验证，单帧压力审计不假装拥有历史。

最终测试数量、压力用例及HTTP结果以[v1.2.4验证报告](../../reports/VALIDATION-v1.2.4.md)为准。尚需官方对局验证共享视野在不同敌阵中的覆盖、实际建筑弹道、擦角与非左上角基地落点、双BOSS真实出生旁移及伤害结算；这些边界没有通过改写任务书或接口文档消除。
