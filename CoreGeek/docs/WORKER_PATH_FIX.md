# log1 / log2 工人往返与建筑位冲突修复

版本0.3.9，2026-09-22。策略/工程修复，涉及R02移动与R03建筑。沿用0.3.8昼夜统一调度，以及用户确认的0.3.7策略基准；没有改变U形墙、升级顺序、敌人掩护判断、维修分工或动态备包。0.3.8修改前状态保存于[源码快照](../../reports/baselines/v0.3.8-source.zip)及[哈希清单](../../reports/baselines/v0.3.8-manifest.json)。

log1共611条decision记录，log2共903条；所有记录的`feedback_failed=0`，所有工人的`stalled`最大值都为0。这说明日志没有记录到动作失败，而旧检测也没有识别往返循环；不等同于每个动作都已得到平台明确成功确认。

旧`worker_jobs`只记录任务名、goal、stalled。普通路线的goal是远处交互站位；`clear_build_cell`没有明确记任务，回合末的兜底记录把动作前的当前位置写成goal。因此不能把不同任务的goal拼成真实行走轨迹。日志没有完整请求、每人真实位置/背包/墙状态或部署版本号，不宣称完整重放了原比赛。

## 2. 可在源码中复现的原因

原先两个模块采用相互冲突的通行规则：

- `Strategy.route`和`WorkerCoordinator.reserved`预留炮位、P站位和当轮目的格，**没有预留尚未建造或被毁的墙位**。
- `clear_build_cell`却把这些墙位认定为不能停留的位置，下一轮会优先把站在上面的工人移开。

于是路线可能让工人走进缺墙位置，下一轮移开逻辑又把他推回原格，再下一轮寻路仍认为原路线最好。每一步都可以合法执行，角色确实移动了，`stalled`自然一直为0。先前的队友让行只能处理占用碰撞，无法消除这两个策略之间的冲突。

按日志目标位置构造右侧基地(30,10)的最小场景后，在修改前0.3.8中复现：

| 重建场景 | 修改前观测位置循环 | 修改后 |
|---|---|---|
| 向石矿(34,10)配送，底边尚未建墙 | `(30,6) → (31,7) → (30,6) ...` | 绕开预留墙位，第5次决策发出collect |
| 从内侧(29,11)去商店(24,20)，顶边(30,12)缺墙 | `(29,11) → (30,12) → (29,11) ...` | 从后方开口绕行，第11次决策买11包WallFixer |

这些位置和地图是用于验证相同机制的重建输入，不是从完整比赛报文恢复的全部状态。采矿场景的第5次决策是重建第19轮，补货第11次是第532轮；不能把它们描述为真实比赛已改善的成绩。

## 3. 统一通行预留

新增`Strategy.movement_reserved(role=None) -> set[Pos]`，作为寻路、诊断、让行和建筑位清理的共同来源：

1. 当轮`ActionPlan.reserved`。
2. 规划的三座炮位。
3. `missing_walls()`返回的待建/待补墙位置。
4. 对工人额外预留开拓者P站位；`role=None`按工人处理。开拓者仍可进入自己的P。

常规`route`、`WorkerCoordinator.reserved`及所有使用其结果的诊断/侧移路线均采用该集合。不能让普通路线绕开了墙位，诊断或让行又把工人送进去。

这是战略预留，不是把“空地”改写为官方实体障碍。`Turn.blocked`、八方向移动、同轮碰撞和`ActionPlan`校验没有变。墙仍在原12个模板位置建造，工人从邻格施工，走后方开口和一格内侧通路。

角色若出生/复活时已经占了预留位，`Routes`仍保留起点；可以离开，但后续不会再走回该位。`clear_build_cell`成功移开后显式记录`clear_site`、被清空的位置、真正下一步目的格和`moving=True`。若周围没有合法空格则等待，不输出非法动作。

## 4. 往返诊断与日志

`GameMemory.worker_tasks[uid]`在原有字段基础上增加：

| 字段 | 含义 |
|---|---|
| `recent_positions` | 最近连续观测的最多4个实际位置；不会用计划目的格代替 |
| `oscillating` | 最近4个位置呈A、B、A、B且A≠B时为True |

原`stalled`继续表示上一轮计划移动但角色未改变位置；它与两格往返是不同现象。任务改变不会抹掉连续位置记录，缺报或过期/死亡清理会断开历史，避免把跨多轮或复活前后的坐标拼成假循环。

`oscillating`仅用于诊断，不会强制工人随机走动，不会覆盖紧急维修或安全约束。合法绕行/让路也可能短暂出现相似形状，需要结合具体任务判断。

保留原`decision ... worker_jobs=...`日志，同时新增每轮一行`worker_motion`，只包含最多两名存活工人的摘要：

| 字段 | 排查用途 |
|---|---|
| `position` | 这轮观测中的实际位置 |
| `job` / `target` / `goal` | 正在做什么、交互对象和最终站位 |
| `command` | 实际发出的官方动作；move内坐标才是这轮下一步 |
| `last_action_ok` | 平台返回的上一轮结果；None表示未提供，不冒充成功 |
| `oscillating` | 连续实际位置是否形成两格循环 |

不打印完整请求、任务内容或沙盒输出，不增加HTTP字段。排查时先看position/command，再看goal；不能再把goal当作下一步位置。
